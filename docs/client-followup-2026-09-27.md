# Правки интерфейса и итогового договора — 27.09.2026

- Стартовый экран: компактные нумерованные шаги, разделители и единая типографика вместо крупных маркеров; статичный фон, без прокрутки.
- Вставка реквизитов: убраны два указанных пояснения, добавлены отступы до и после поля. Парсинг остаётся локальным, перенос и сохранение требуют явного действия.
- После принятия раннего приглашения показывается только ФИО присоединившегося; старые инструкции и уведомление отправки скрываются.
- В карточке реквизитов можно выбрать сохранённый профиль и проверить его перед подтверждением. Повторно вводить паспорт не требуется.
- Все загрузки добровольные. Исторические обязательные требования и статусы проверки файлов больше не блокируют согласование. Старые личные файлы не становятся общедоступными. Проверка формата/размера, авторизация и контроль целостности сохраняются.
- Статусы ручной проверки убраны из списка файлов и шкалы доверия; административная запись решения отключена (HTTP 410). Исторические записи остаются в базе и журнале. Общие приложения включаются в итоговый архив независимо от прежнего статуса ручной проверки.
- Приёмка при личной встрече с явным подтверждением принимается; простой осмотр без подтверждения по-прежнему требует уточнения.
- Итоговый неподписанный договор редактируется в одной модалке. POST `/deals/:dealId/text-versions` проверяет структуру, ФИО из профилей, незаполненные места и основные условия. Это локальная проверка полноты, не юридическая экспертиза и не универсальная проверка смысловых противоречий; текст не отправляется внешнему ИИ.
- Новая версия содержит именно отредактированный текст, не перегенерацию. Старые ответы анкеты не подменяют её условия. Сохраняются история, optimistic concurrency, сброс прежних согласований и запрет изменения после первой подписи. ФИО проверяются повторно при согласовании. Подписание и PDF используют замороженный текст актуальной версии.

## Проверки

Покрыты unit/API-тестами: необязательные загрузки, отключение ручной проверки, обе фразы о приёмке из обращения, сохранение текста новой версии, запреты на чужую/устаревшую/подписанную редакцию и ошибки полноты.

Браузерные проверки используют изолированные локальные фикстуры: мобильная вёрстка, отступы вставки, профиль, приглашение, отсутствие статусов проверки файлов, сохранение текста при ошибке редактирования, сохранение новой версии.

Полный legacy browser/integration lifecycle по-прежнему содержит сценарии прежней обязательной проверки файлов и требует отдельного обновления. Реальные паспортные данные, клиентские сделки и отправка документов в MAX для тестов не используются.

## Реквизиты в PDF и единый раздел условий

- Заголовок экрана — «Документы», без «по желанию»; загрузки при этом остаются необязательными.
- Новые снимки `deal-signature-v2` включают паспортные поля, дату рождения, адрес регистрации, email и подтверждённый телефон из профилей. Телефон выводится номером, а не внутренним UUID. Паспортные данные не передаются в генератор ИИ.
- Полные реквизиты доступны участникам в просмотре договора до согласования. Их хеш отправляется с согласованием; устаревший просмотр отклоняется. Снимок фиксируется при первом согласовании, обе стороны согласуют одинаковые данные. Изменения профиля не меняют этот снимок. Для исправления нужна новая редакция и повторное согласование.
- Телефон подписания должен соответствовать снимку v2. ФИО в подписях нового PDF также берутся из снимка, а не из изменяемого профиля.
- Исторические снимки v1 и уже сохранённые PDF/ZIP не переписываются и не дополняются текущими паспортами. Исправление не меняет ранее подписанный пользователем архив.
- При новой генерации сервер создаёт один авторитетный раздел «Условия договора» из всех подтверждённых ответов. Повторный AI-раздел «Условия сделки»/«Условия договора» отбрасывается; остальные разделы сохраняются без точных дублей подтверждённых пунктов. Большие анкеты разбиваются на продолжения без потери ответов. Ручные редакции этим преобразованием не затрагиваются.
- Проверены синтетический PDF (включая длинные поля), мобильный просмотр реквизитов и регрессии хеширования/согласования. Неполные необязательные поля не выдумываются.

### Режим подписи

На сервере проверены только несекретные значения: `SMS_PROVIDER=max-test`, `CONSENT_ELECTRONIC_SIGNATURE_VERSION=stage-pep-v1`; SMSC не настроен. Поэтому PDF корректно показывает `MAX_TEST` и `stage-pep-v1`. По явному решению пользователя от 27.09.2026 тестовый режим MAX оставлен, конфигурация подписи не менялась. Это не перевод сервиса в рабочий SMSC-режим и не заключение о юридической действительности подписей.

## Повторные правки: Android, этапы сделки и присутствие

- Первый экран содержит описание, роль и приглашение. Продолжение доступно после подтверждения отправки приглашения или присоединения второй стороны. Открытие окна MAX само по себе не считается отправкой: пользователь подтверждает «Я отправил приглашение». Подтверждение сохраняется в `deal_invitations.sent_at`.
- Реквизиты вынесены на отдельный этап `REQUISITES` перед параметрами. Выбор готового профиля — четвёртый способ, только при заполненных обязательных паспортных полях. На ожидании второй стороны повторная форма не показывается. Вместо «Шаг N из 5» используются названия этапов.
- Загрузка материалов перенесена к параметрам сделки. Паспортное требование шаблона скрыто; остальные приложения дополнительны. Добавлены отступы. Текст приглашения включает конкретный предмет из описания/ответов с фильтрацией явно личных сведений.
- До готовности данных договор недоступен для просмотра. Для ответственного за материалы плитка называется «Загрузите материалы сделки»; пустое состояние другой стороны называет соответствующую роль. Нижние дублирующие кнопки «Документы сделки» убраны. Заголовок подписания — «Подпишите и сохраните».
- Присутствие обозначено явно как «В сети в приложении»: heartbeat видимой вкладки каждые 30 секунд, порог 75 секунд. Это не статус аккаунта MAX; скрытая вкладка перестаёт обновлять активность.
- Android-приглашение открывает документированный MAX `:share` непосредственно из пользовательского нажатия. Есть видимая запасная ссылка и явное подтверждение отправки.
- Скачивание в мобильном MAX использует `WebApp.downloadFile`, а не неподдерживаемый обычный `href`. После подготовки ссылки отдельное нажатие сохраняет требуемый пользовательский жест. Отсутствие метода/ошибка MAX отображаются пользователю.
- Нативному загрузчику не требуется cookie WebView: ссылка выдаётся авторизованному участнику на конкретный файл на 120 секунд. В Redis хранится только хеш токена; при получении повторно проверяются сессия и доступ к файлу. Ответы не кэшируются, query string скрыт в серверных журналах. Обычные браузерные скачивания сохраняются.
- Проверки: unit/API-тесты доступа, срока и отзыва ссылки, HTTP-валидации и заголовков; 28 браузерных регрессий, включая этапы, пустые материалы и имитацию Android bridge. Реального подключённого Android нет: проверка на Android 15 внутри MAX остаётся за клиентом. Последняя сохранённая Android-подпись содержит `Android 12` в User-Agent; фактическую версию ОС это не подтверждает.
